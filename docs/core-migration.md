# Rust 核心与 Go 扩展迁移（WIP）

分支：`wip/rust-core-go-extensions`。起点：`b5eae618cf2a962466c871b729f5761beb064084`。
这是替换旧 Rust 后端的新迁移，不是继续复制整个 Go 后端。
**保持 Draft，不合并、不上线、不改生产密钥、用户余额或数据库。**

## 本批完成范围

旧 Rust 后端整个源码树、其独立迁移器、测试、AUR 包、环境样例、路由门禁脚本
及旧部署说明均被移除。Go 回归测试仍需的三个 JSON 样例移到 `contracts/go-regression`。
当前 Go/Web 服务、发布流程、安全校验和独立 `apps/lmm` CLI 保留。
原生部署命令仅接受 Go，拒绝旧 Rust 包与链接目标；不能用此分支接管一个尚未结束的
历史 Rust 部署事务。此类事务应先使用其已验证的旧操作程序人工恢复。

新增：

- `apps/core-rust`：个人/团队账号、成员角色、逐 Key 付款顺序、付款偏好、整数额度、
  不可变费用归属，以及进程健康检查、安全关闭和业务拒绝入口。
- `apps/extensions-go`：独立 Go 模块宿主，显式注册、路径隔离、服务凭证、请求体上限，
  支持独立启动和关闭。没有数据库句柄或模型转发入口，目前注册列表为空。
- `contracts/core/v1`：由现有 Go 规则与新 Rust 规则共同消费的 24 组付款边界样例。
- `deployment/docker`：两套独立 Compose 项目和构建上下文，非 root、只读文件系统、
  内存/CPU/进程约束；更新扩展的命令不包含核心服务。

**这些是已实现的规则和服务基础，不是完成的业务后端。**
Rust 的 `/health/live` 返回 200，`/health/ready` 与业务接口返回 503。
没有允许接流量的环境开关。没有持久化用户/团队、账本或上游转发实现。
现有 Go 业务尚未移进模块宿主。测试“核心容器没重启”不等于“真实模型流不断”。

## 服务权属

| 范围 | 最终唯一负责方 | 边界 |
| --- | --- | --- |
| 用户、登录、会话、API Key、OAuth 授权和撤销 | Rust 核心 | Go 扩展不得通过修改数据库绕过权限。 |
| 个人/团队账号、成员关系、消费授权、预算 | Rust 核心 | 操作人、Key 所属账号、付款账号分开保存。 |
| 价格、计费、预留、结算、退款、订阅抵扣 | Rust 核心 | 同一事务校验权限、额度和预算；整数记账。 |
| 渠道、模型路由、转发、协议转换、流式输出 | Rust 核心 | 请求关键路径不得同步调用 Go；不重读付款人。 |
| 工具市场、活动、推荐、通知、外部集成、辅助控制台功能 | Go 扩展 | 通过有版本、有权限限制的核心接口工作；不另建账本。 |
| 支付平台接入、邮件等易变适配 | Go 扩展 | 核心按原始凭据、订单和幂等记录确认入账，不能信任任意金额通知。 |

初期只拆“一个核心进程、一个扩展宿主”，不拆出大量细服务。
Go 模块用显式接口注册，不把 Go 动态库或任意脚本装进 Rust 进程。
不同模块可逐步拆成独立 Go 服务；核心接口版本不随每次模块发布而变化。

## 核心不依赖扩展可用性

模型请求路径是：验证 Key 与账号 → 检查价格和预算 → 原子预留 → 固定路由/付款信息
→ 协议转换与上游转发 → 记录用量并结算。没有“先找 Go 确认用户或扣费”的步骤。

配置更新通过受限的内部接口提交。核心持久化并验证已生效配置；Go 不可用时保持
最后的有效配置。通知、统计展示等扩展事件由核心事务同时写入事件待发记录，
事务成功后再发送；消费者去重，失败可重放。队列必须有上限，不能在内存无限积压。
事件投递不是账本，重复事件不能重复扣费。不得将未知资金状态当作免费请求。

服务凭证只表示“哪个模块”。涉及用户的操作仍需验证用户、账号、实际权限和版本。
不能相信来自浏览器的用户等级、付款人或成员授权字段。共享网络不等于可信调用方。
内部接口初期以版本化契约为先，传输编码可独立演进；本批尚未暴露可写核心接口。

## 团队是原生账号，不是假用户

延续 [团队设计](team-accounts.md) 和独立 Draft PR #656，不合并或覆盖该 PR。
本批只同步已存在的规则；其成员数据库和完整资金链需要后续在核心落地。

个人仍是登录人；团队没有共享密码。一个人可拥有一个团队、加入多个团队。
账号统一由 `kind + id` 标识；同为 7 的个人与团队不是同一账号。
平台 L0–L6、团队成长等级和 owner/admin/member 成员权限不能混用。
L5 管理员、L6 超级管理员不能因此自动花某个团队的钱。团队不继承创始人的平台权限。

个人 Key 默认只用自己；主动配置后才可按顺序使用已获得消费授权的多个团队。
团队 Key 只能使用所属团队，不能回退到创始人钱包或另一个团队。
第一层是逐 Key 付款账号顺序，第二层是每个账号自己的订阅/余额顺序。
个人 Key 不能覆盖团队的订阅偏好；新 Key 的默认值与旧 Key 迁移后的行为分别处理。

请求开始前校验完整列表，禁止重复、负数 ID、其他个人账号及未经授权团队。
开始后固定一个付款账号、价格版本、预算周期和订阅/钱包分项。
流式输出、上游重试、重复回调、退款不能再选择另一个付款人。
只允许明确且已回滚的余额/额度不足尝试后续已授权账号；撤销、停用、权限错误、
数据库错误和未知结果必须停止。跨账号拼单、成员退出后把已发生费用转给个人均禁止。

保留现有每美元 500,000 credit 的单位。额度运算检查负数与溢出，不使用浮点数结算。
当前 `Credits` 表示非负额度数量，不表示已经实现完整钱包，也不禁止未来账本表达
欠款：负债必须有明确类型与审计规则，不能把异常数值默认为零。

## 迭代阶段与验收

| 阶段 | 内容 | 完成条件 |
| --- | --- | --- |
| P0，本批 | 删除旧 Rust、服务分离、原生账号规则、Docker 开发栈 | 规则交叉测试、构建和容器独立重建检查；不能接生产。 |
| P1 | 持久化用户、Key、会话、团队与成员关系 | 保留旧 Key 和授权版本；撤销立即生效；并发成员操作回归。 |
| P2 | 账本、预算、订阅、预留/结算/退款、幂等恢复 | 并发不会多扣；重复与乱序回调不重复结算；重启后可对账。 |
| P3 | Go 路由和协议转换分批移植 | Chat Completions、Responses、Messages、Gemini、SSE/WebSocket 的真实兼容测试。 |
| P4 | Go 业务逐模块迁出 | 核心表只有一个写入方；扩展崩溃不影响模型请求；模块单独发布。 |
| P5 | 旧数据迁入、双核心切换与回退演练 | 旧 Key 无需更换，资金与权限一致，长流结束后退出旧实例，通过验收后再申请上线。 |

每批只认实测结果，不把“代码写了”“有健康检查”“Compose 能启动”当作全量完成。
先用隔离数据副本做回归，不用生产数据库测试。迁移期间继续由现有 Go 服务处理生产。
必须按账户/请求明确唯一账务写入方，禁止新旧核心对同一请求同时扣费。

## 发布与连续输出

普通更新只构建、部署 Go 扩展。核心无代码/配置变更时不重启。
Rust 核心升级需要至少两个健康实例：新实例真正就绪后接新请求，旧实例停止接收新请求，
保持已有流式连接和结算，等待结束再退出。HTTP 头、空闲和请求总时限必须分别定义，
不能为了部署方便给所有流设置过短总超时。有限的关闭等待期仍可能中断超长请求；
这需要明确的超时处置政策，不能声称单实例或任何故障下绝不掉流。

核心与扩展镜像应分别编号、锁定摘要、验证来源。扩展发布不得自动迁移核心表。
数据库改动先扩展，验证新旧代码兼容后再移除旧结构；账务回退不能靠恢复旧快照丢弃新交易。
本批只有开发镜像构建与 Compose，没有发布生产镜像、迁移生产数据或改动线上反向代理。

开发命令、密钥处理、当前限制与容器验收见 [Docker 指南](../deployment/docker/README.md)。
