# 原生账号：等级、平台管理与团队权限（WIP）

本设计接续已合并的 #613，配合 [团队需求与付款规则](team-accounts.md) 使用。
本批基线为 `8e0f88de5a4f979b8e6cd7ecd45c0dac8c747b1e`。
**本批交付共用账号标识、范围检查、等级适配器和测试，不交付可用的团队系统。**
没有数据库迁移、线上入口或实际团队扣费，也没有恢复 L1 申请／推荐信流程。

## 1. 原生概念不是多一个 `is_team`

`User` 表示真实登录身份；`Account` 表示资源和资金归属。一个用户持有个人账号，
可创建并持有一个团队，也可加入多个团队。团队没有密码、OAuth 登录或浏览器会话。
个人和团队共用钱包、订阅、Key、计费、主页和徽章功能，不各复制一套实现。

统一使用 `pkg/account.Ref { kind, id }`，而不是在计费包中私有定义 Account。
`accountfunding.Account` 保留为类型别名，JSON 格式和旧付款顺序兼容。
`personal:7` 与 `team:7` 不同；数据库外键、缓存和查询必须同时包含种类和 ID。
个人 ID 继续对应旧 user ID；团队不插入伪造的 `users` 行。handle 是可变公开名称，
不能作为资源归属、权限或收款的依据。

分开保存以下信息，禁止互相覆盖：

| 信息 | 含义 | 可信来源 |
| --- | --- | --- |
| actor / responsible user | 登录操作人，或 API Key 的负责人 | 验证后的会话／Key 记录 |
| active account | 当前控制台视图 | 请求选择 + 服务端成员校验 |
| key owner | Key 归属的个人或团队 | Key 记录，不随账号切换变化 |
| payer account | 本次实际付费账号 | Key 的显式排序 + 消费授权 + 成功预留 |

API Key 能证明凭证和负责人，不能声称识别了现实中的实际使用人。
主站 `UserId` 不得替换成团队 ID 或创建者 ID。账号切换不改变登录人、全站角色、
Key 归属、已创建订单或已开始请求的付款人。

## 2. 保留 L0–L6，但拆开权限含义

现有 `model/trust_level.go` 和 `model/trust_level_config.go` 已明确区分成长等级与
角色等级。继续复用 `TrustLevelBenefits` 配置、净真实支付额度、活动衰减、管理覆盖、
权益显示及折扣；不复制阈值或用当前汇率重算历史成长。

| 范围 | 等级 | 权限来源 |
| --- | --- | --- |
| 个人普通账号 | L0–L4 | 该账号的激活／净真实支付／活动／覆盖记录 |
| 个人全站管理员 | L5 | 现有全站管理员角色；不能靠充值获得 |
| 个人超级管理员 | L6 | 现有超级管理员角色；不能靠充值获得 |
| 团队账号 | L0–L4 | 团队自己的事实，使用同一份成长配置 |
| 团队内角色 | owner / admin / member | 成员关系，不是 L5/L6 |

团队创始人拥有最高团队权限，但不是超级管理员。团队管理员不是全站管理员。
创建者个人 L4、L5 或 L6，都不能把等级、折扣、分组或管理权限带给团队。
团队最高只到 L4，也不能通过人工覆盖写入 L5/L6。移交团队不改变团队等级。
个人管理员现有 L5/L6 展示和权益保留；本批不改变个人评估函数。

团队直接充值的成长只计入团队，记录操作人但不同时给操作人加成长。
内部转账、赠额、红包、邀请奖励和余额搬运都不生成新的真实支付事实。
退款沿用现有净支付口径冲减原受益账号；不得循环转账刷等级。
订阅付款是否计入成长继续沿用现有订单分类，不能为了团队功能偷偷放宽口径。
团队活动取团队自己的 API 活动；成员个人调用不算团队活动。

新的 `model.EvaluateTeamAccountAccess` 不接收创建者或全站角色。它调用现有
`evaluateTrustLevelCredits` 的普通账号分支和同一份 `DeveloperAccessPolicy`，
没有创建虚假团队 User，也没有第二套折扣／衰减算法。输入仍需由未来的账号存储层
从团队自己的记录加载；当前适配器不能自行证明这些事实或授予成员权限。

## 3. L0 与加入团队不能互相阻塞

自然 L0 用户可以接受邀请、查看自己的团队、进入已激活且已授权的团队工作，
其个人账号仍是 L0，不更新个人 `console_activated_at`，也不补发个人奖励。
创建团队本身不获得 L1；团队 L0 的创始人可以配置资料、充值、管理邀请，
但不能仅凭创始人身份调用付费 API。

团队按现有激活规则，使用团队本身的真实支付或平台明确授予的账号激活记录。
个人转入团队的余额不自动伪装成真实支付或升级，界面须说明余额与激活的区别。
不得重新加入已经移除的申请信、推荐信或旧申请待办机制。

个人 L0 的成员在团队范围内创建／使用团队 Key。未来若允许该成员创建个人归属的
团队付款 Key，必须显式使用已授权团队范围，不能借此默认启用个人付款权限。
所有加入、Key 创建、OAuth 同意和 `/models` 等入口必须使用所操作账号的访问决定，
不能先统一用个人 `IsConsoleActivated` 拦掉团队入口；也不能反向升级个人账号。

“自然未激活”与“被平台限制”不同。停用用户、撤销会话、重置认证版本、明确的安全
限制优先于所有团队授权。`Actor.Restricted` 必须由服务端真实状态产生，不能由客户端
传入，也不能只凭 `level == 0` 推断。既有人工回退 L0／安全重置的限制，在能可靠区分
作用范围之前，保守阻止团队消费；迁移测试不得让团队成为绕过旧限制的入口。

## 4. 全站管理与团队自助是不同入口

现有 `service/authz.Can` 对 superuser 提前放行，其 Casbin 规则没有团队范围。
不能用 `Can(...) || isTeamMember` 之类条件授权团队接口，也不能把 `team:42:admin`
塞入现有全站角色集合，让角色并集扩大权限。

全站管理继续使用现有 `AdminAuth` / `RootAuth`、权限注册表、覆盖规则和审计。
新增平台侧“团队管理”资源时，普通全站管理员仍需该资源权限；超级管理员走现有
全站授权。可按权限查看、冻结、处理团队，不自动成为团队成员，更不自动获得
消费团队资金或以团队身份发帖的能力。敏感代管动作需要单独操作、二次验证和理由。

团队自助入口使用真实用户 + 明确账号范围 + 有效成员关系 + 具体动作权限。
`account.ResolveScope` 不接收全站角色，零值和错误结果没有权限。管理员或 root
没有成员关系时，不能从自助入口进入团队。不能把一个接口返回的允许访问快照
当成永久授权；写入与资金预留事务里需重新验证。

创始人可管理管理员／成员；管理员仅管理普通成员；同级管理员互不管理。
`CanManageMember` 只是现有其他成员的层级检查，不是提升角色、移交所有权、
查看对话、导出资料、转账或购买套餐的授权。`CanManageTeam` 仅开放管理区域。
自我预算、上级预算分开保存；三种团队角色均不能跳过上限和已用额度。

资金转出、套餐购买／续费另有授权和限额，默认只有创始人；管理员需明确授予。
所有团队角色使用资金都需要有效消费授权。成员总用量不能因换 Key 而清零。
平台管理员在团队中只是普通成员时，也只能按该成员权限和预算使用资金。

## 5. 等级、分组、Key、套餐如何共同决定调用

等级是账号权益，`group` 是现有模型／路由／计价分组，团队角色是操作权限。
三者不能互相赋值。购买套餐的分组升级／到期回退作用于订阅所属账号，
不能修改操作人的私人分组，也不能给其他团队开放模型。

每次请求依次检查：登录人或 Key 负责人可用、Key 本身有效、全部显式付款来源授权
有效、候选账号访问权限与分组允许、模型/IP/OAuth 范围允许、预算和余额可预留。
付款人的账号等级与分组决定该次报价；不能先享受个人 L6 折扣，再让团队付款。
保留现有价格锁、服务等级加速价格与套餐规则的优先级；团队不能跳过它们。

沿用 #613 的两层排序：逐 Key 的账号顺序 + 付款账号内部四种订阅／钱包偏好。
个人 Key 默认仅个人，主动配置后可以使用多个授权团队；团队 Key 只能使用所属
团队自己的余额／订阅。不能增加隐含的个人兜底。

单次请求只选一个付款账号。预留不足时才尝试下一明确配置的账号；账号访问被拒、
成员撤销、模型禁止、数据库异常或不确定扣款结果都停止，不当成余额不足。
个人 L0 未获调用权限时，应选择有效团队范围，而不是靠跨账号回退掩盖个人拒绝。
一旦发送，固定付款账号、价格／策略版本、订阅与钱包分项、预算周期和负责人。
补充预留需重验；已发生的费用与退款始终归原账号。

日志明确列出 Key 归属、付款账号、负责人及分项金额。个人支付不消耗团队预算，
团队支付则合并该成员所有 Key 的团队用量；Key 的总限额跨账号持续有效。

## 6. 存储、接口、页面的共同边界（尚未迁移）

目标结构是 `accounts` 统一账号与资源归属，`users` 保留登录／全站角色，
`teams` 保存团队资料与负责人，成员关系单独保存。账号可使用 `(kind,id)` 复合主键，
资源通过同一复合外键引用；不能让某张表把裸 ID 当作完整账号。
数据库需约束每人一个个人账号、每个团队恰好一个 owner、成员唯一、全局 handle 唯一。
团队所有权变更必须在一笔事务中维持唯一 owner，不允许先删后补留下无人负责的团队。

钱包、套餐、订单、Key、用量、转账和公开主页复用已有表或服务，逐步补充账号归属。
先回填个人归属并对账，再开放团队写入；不得在每次启动重新回填或重算成长。
旧 `user_id` 各字段需逐处确认原意：有的是操作者，有的是资源归属，不做机械替换。
旧 `/self` API 保持个人含义，新的账号范围入口显式携带账号引用；不能用全局请求头
使旧接口偷偷从个人钱包切到团队钱包。路径中的账号 ID 也只是选择，不是授权。

前端保留 `auth.user` 作为登录人，另有当前账号视图；缓存键同时包含登录人与账号。
页面组件接收账号能力，钱包、套餐、Key、徽章复用同一视图，而不是成套 Team 页面副本。
切换时取消旧视图请求，避免旧响应覆盖新账号。不同标签页可保持不同账号。
充值／转账确认页绑定创建时账号；切换视图不能改变已创建订单的受益方。

菜单分别显示：当前账号 `团队 A · L2`；你的团队身份 `管理员`；
仅具备全站权限时出现独立的 `平台管理` 区域。团队管理与平台管理不能都只写“管理员”。
新增 Key 管理、我的团队、加入团队、账号切换。成员看到自己的 Key、预算和用量；
团队管理入口仅 owner/admin 可见，内部动作继续按权限检查。

`/@handle`、银行卡比例身份卡、头像和徽章都基于同一个 Account。
个人和团队共用名称空间、每月改名限制及保留词校验。公开主页不直接返回内部账号对象；
余额、成员邮箱、私有成员关系、调用明细和平台管理能力默认不公开。
SVG 分享保持主动开启和撤销机制。视觉仍沿用首页的留白、清楚字体与轻量粒子效果。

## 7. Go / Rust 与核心服务

当前先以已有 Go 计费、访问和全站权限实现为兼容基线；不把团队完整复制到第二套后端。
`pkg/account` 是无数据库／网络／页面依赖的领域边界，不是新微服务。
Rust 的 `DashboardUser` 也仍含个人 role/group/quota；后续必须同样保留登录人，
增加独立账号范围，而非把团队塞进 DashboardUser。

后续核心服务拥有账号消费授权、报价快照、预算预留与账本结算的最终决定。
邀请、handle、徽章、页面属于扩展功能；扩展功能可以请求变更，但不能自行确认扣款、
改余额或授予全站角色。先形成清楚模块边界，再决定是否独立进程，不为了团队功能
增加不必要的微服务或将每个付费请求依赖于所有扩展服务。

跨服务协议携带固定账号引用、负责用户、Key、策略／成员版本、请求 ID 和截止时间。
核心验证调用服务身份并检查当前授权，不能信任任意插件传来的角色或“已付费”布尔值。
撤权与新预留必须有明确的先后关系；失联时停止不能确认的新消费，但继续对账已发生费用。
无法承诺进程永不崩溃；以持久化记录、重复请求保护和恢复测试保护账务。

Go/Rust 使用同一组账号范围、角色隔离、付款和预算用例验收。在 Rust 完整支持前，
带团队归属或新版付款策略的 Key 必须在进入旧个人处理前明确拒绝，不能静默忽略字段。
新增表／列不等于旧二进制安全：开户和发 Key 前必须完成后端能力门禁及旧版本回滚测试。

团队套餐不改变成员个人分组；旧 Key 无团队兜底；同 ID 不同 kind 绝不串账。
